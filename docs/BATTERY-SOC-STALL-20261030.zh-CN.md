# 电量长时间停留核查（2026-10-30）

## 报告与结论边界

用户报告畅行60有时停在80%很久后才下降、K1有时停在4%很久；另有转述称
开机2%固定、FGU库仑量上涨、CM报 `failed to enable primary charger, ret = -22`、
`chgr_type = 0`。转述缺少机型、安装包版本及原始日志，不能把三者认定为同一故障，
也不能认定所有机型均已复现。当前电脑 `adb devices -l` 为空，本轮没有实机部署、
改写SOC、调整充电电流或进行完整充放电验收。

机型已准备的源码。实际原厂证据沿用以下记录，不把供体源码当作其他型号的实测：

- [E5原厂充电/SOC证据](E5-CHARGING-SOC-20261021.zh-CN.md)：Android13
  `2024112822`，原厂AW和CM二进制哈希及使能、JEITA、保留区行为。
- [K1原厂证据与尚未复现的低SOC问题](../devices/k1/SOC-CHECK-20261029.zh-CN.md)：

## 核对转述中的因果关系

1. `cm_batt_works()` 定时读取FGU，经平滑更新 `desc->cap`，然后重新排队。
   它不是只在充电状态迁移时执行。关键读数失败也走重新排队出口；正常退出后
   只有正式shutdown标记会阻止再次排队。
2. `NOT_CHARGING` / `DISCHARGING` 分支禁止显示SOC上升。因此真实充入而CM
   误判未充电，确实可能表现为百分比停住。工作仍在运行与工作彻底停止需要分开。
   同理，放电时保留UI低于原始SOC，可以先停留再下降，不能单凭停留时长定性。
3. CM的 `charge_counter` 来自 `cm_get_charge_now()`，本质为设计容量乘显示SOC，
   不是独立读取的硬件库仑计。拿它除以 `charge_full` 得到同一个百分比，不能作为
   第二份证据证明“启动残值”或硬件精度。
4. `cm_primary_charger_enable()` 直接调用芯片的CALIBRATE使能属性，不检查
   `chgr_type`。UNKNOWN是识别结果，不能只凭它推断 `-EINVAL` 来自哪里。
   需要区分不支持的属性、初始化/参数错误、温控和实际BC1.2识别。
5. 界面按电流方向显示“充电”不能证明CM控制状态正确；不能以此替代驱动修复。

## 本轮确认并修复：E5使能回读属性未注册

E5的 `aw32257_power_supply_get_property_locked()` 已实现CALIBRATE读取真实
CE/HiZ/boost，但 `aw32257_power_supply_props[]` 没声明此属性。
当前 `power_supply_core.c::__power_supply_get_property()` 先检查描述符，未声明
就直接返回 `-EINVAL`，不会进入AW getter。CM因而读不到已开启状态，反复认为
主充电器没开启并重新发送使能命令。

修复在 `devices/e5/charger.py::apply_state()` 中补齐属性声明，同时覆盖已经
应用 `e5-aw32257-state-v2` 的缓存；重复准备不会重复插入。这里CALIBRATE是
充电芯片原有的使能接口，不是FGU校准操作。不改变原厂电压、电流、JEITA或UI
平滑规则。它只适用于E5的AW32257，其他芯片已经声明其原有使能回读接口。

此缺口直接证明的是“回读被内核拒绝”，**不能把它写成已复现并修复转述中的
使能写入-22，更不能据此宣称畅行60/K1的停留已解决**。

## 仍未确认

畅行60的80%停留和K1的4%停留需要故障同一时刻的CM SOC/状态、FGU
`bat_soc`/`normal_temp_cap`/`cc_uah`、电压/OCV/净电流、工作日志与固件版本。
现有证据不足以区分真实积分很慢、历史UI/原始SOC基准差异、低SOC校正、充电
状态误判和工作停止。不能根据端电压直接重写百分比，也不通过取消原厂平滑、
强制充电状态、增加后台强制校准或禁用休眠来掩盖。

后续已在畅行60捕获启动UI/normal基准不一致，并补入公共POCV检查；
原厂差异、适用机型及验证边界见[公共修复记录](BATTERY-BOOT-OCV-20261031.zh-CN.md)。
