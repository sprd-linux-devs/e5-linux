# 公共电量基准修复（2026-10-31）

## 实际问题与修复范围

畅行60本轮启动保留的UI为25.4%，FGU温度基准为94.6%；电量显示依照原厂平滑
追赶错误的高基准。约13分钟的电流积分仅约276mAh，显示却增加45.5个百分点。
详见[现场记录](CHANGXING60-SOC-20261031.zh-CN.md)。这与“充电设置2.5A是否
生效”是两件事；现场已确认DCP输入2500mA、电池CC量化2460mA。

公共FGU补入较新原厂驱动的POCV一致性检查：只有已有启动校准条件全部满足后，
才读取实时OCV；与保留POCV相差超过300000µV，或读取失败，不做该次校准。
不改电池表、温度/静置时间条件、校正余量、积分或UI平滑，不按单次电压猜SOC。

所有使用公共FGU准备路径的机型都会带入：E5、T551M、M8、T512N、远航41S、
K1、LYM-10K、畅行60。机型DT中的 `support_boot_calib` 及原有其他门控仍然生效。
远航41S原来独立实现的同一检查已移到公共路径；既有源码缓存中的旧检查会在
暂存校验时迁移，重复准备不会叠加。无法识别的旧块会拒绝，原源码保持不变。

这是将已核实的新原厂FGU检查回移到公共驱动，**不是声称所有旧原厂驱动本来
都有此检查，也不是证明所有“卡百分比”都由同一个原因造成**。

## 回归与边界

`test_boot_soc.py` 编译实际启动校准和启动恢复函数，覆盖正负300mV边界、
读取失败、温度上下界、关机899/900秒、现场113秒短重启、正常校正30/1000余量、
UI/原始SOC分别保留、旧41S缓存迁移与重复准备。去掉新增检查的负向对照必须失败。

`test_battery_periodic.py` 编译各模型已准备的完整CM定时工作函数，覆盖2%、4%、
40%、80%在状态不变时持续充放电、临时关键读取失败后恢复、充满、关机，及
错误Not-charging分类下UI保持但工作持续的场景。后者是原厂方向限制，不能
用测试证明充电器类型已经正确识别。该测试不修改这一策略。

另保留PMIC两保留区编码/反复保存、实际电气满充校正、JEITA温区及电量算术
回归。E5的AW充电使能属性补齐描述符，测试通过真正的power-supply core分发，
不再只测getter。此项是已确认的软件接口缺陷，不能等同于所有型号的SOC根因。

## 不能承诺的部分

畅行60本次启动在113秒静置时间门控就停止校准；94.6%的历史基准在该启动之前
已经存在。新增检查防止后续使用陈旧POCV，不会自动修复一个编码合法但历史
错误的SOC，也不会强行将UI和原始SOC设为相等。原始损坏发生时刻尚未捕获。
恢复仍依靠原厂允许的有效OCV/满充端点校正；没有向机器写入猜测的百分比。
源码回归、编译通过不代表所有电池都完成充放电精度实测。
