# 近期 CPU／内存占用排查

## 实机证据与范围

本轮只读测量的是当前连接的 F50 Pro，内核为 `6.12.94-u30pro-p1`；
没有关闭服务、重启、热部署或切换电脑网络。两轮各 20 秒的 `/proc/stat`、
`meminfo`、进程 CPU 和 `smaps_rollup` 采样中，整体 CPU 为约 0.4%～0.9%，
可用内存约 1.22 GiB。较晚一轮匿名页约 51 MiB，三项主要后台的 PSS
与前一轮基本相同。没有复现持续高 CPU，也没有足够证据宣称存在内存泄漏。

采样期间设备还运行着终端和 `top`，不是严格控制的关闭全部网页的空闲基准。
没有同一设备的旧版对照；不能把这份结果说成三个系列都已完成实测。
原始诊断保存在本机 `work/resource-usage-20261120/`。

| 当前 F50 Pro 进程 | 实际分摊内存 PSS | 采样 CPU | 源码判断 |
| --- | ---: | ---: | --- |
| 蓝牙 Python 网关 | 约 19 MiB | 接近 0 | 蓝牙关闭时控制后台仍常驻；MU300／Pro 使用这套实现，E5 不同 |
| 来电通知 Python 后台 | 约 12 MiB | 接近 0 | 事件订阅，不能为降低占用切断来电提醒／转发 |
| IPv6 RA 续租 Python 后台 | 约 9 MiB | 接近 0 | RA／netlink／ubus 与到期事件；不应删掉续租恢复 |
| BlueZ | 约 2.3 MiB | 接近 0 | 与 Python 网关分开计量 |

这些是确实存在的常驻开销，不能用 VSZ 代替实际物理内存，亦不能据此
认定它们就是所有反馈的根因。MU300 新增 AUDCP 内存预留还会固定减少
约 9 MiB 可用总内存；它不是运行中的 CPU 消耗，Pro／E5 也不能据此归因。

## 已确认并修复的共同缺陷

三个仓库的流量管理原先只要存在保存过的 `policy.json`，即使达量保护与
定时重启全部关闭，也每 10 秒拉起 Python，再查询 UCI／netifd。
本轮连接的 F50 Pro 没有这个配置文件，因此该问题不是这台机器采样的原因。

修复包括：

- 策略状态机、RPC 和异步工作进程改为 ucode；直接使用 libuci／libubus。
- 复用现有统计采样回调；关闭功能且没有未完成恢复时不启动工作进程。
- 保留旧配置、断网归属和每日执行凭据；关闭保护仍恢复由策略停用的 WAN。
- 重启网络继续走各平台原来的锁和 SIM scope，不新增 AT reader 或改变所有权。
- 新模块纳入完整包、普通更新和差分路径，验证旧 Python 版本升级及后续更新。

其后已完成三仓库各六轮迁移回归，并修正真实重启入口对外部 `timeout`
命令的依赖；详细范围及证据见 [六轮回归记录](TRAFFIC-POLICY-UCODE-REGRESSION.zh-CN.md)。

实机没有部署这轮修复，不能把离线通过称为硬件验收。已经生成的发布包也不
包含本轮新改动。蓝牙、来电通知和 RA 的现有 Python 实现尚未迁移，不能把
流量策略的完成描述成所有后台已改完。后续固件运行时代码使用 ucode，优先
既有事件与到期定时器；Python 仍可用于主机构建、离线诊断和测试。
